# ADR-007 · 同步协议与密文 blob 格式

| 项 | 值 |
| --- | --- |
| **状态** | 已采纳（Accepted） |
| **日期** | 2026-10-30 |
| **决策者** | 主理人 / 架构师 / 工程师 |

---

## 背景

同步是 LifeHub 从「单设备记账工具」走向「跨端工具」的关键一步，
但它也是**隐私红线最容易被突破**的一步。

核心层已经实现了两块能力：

- `packages/core/src/services/sync/sync-payload.ts` —— 构造同步载荷，
  只接受 `EncryptedBlob[]`，并用 `assertCiphertextOnly()` 递归断言「载荷里没有明文字段名」；
- `packages/core/src/services/sync/merge.ts` —— 三方合并，
  字段级 LWW 决胜键为 `(updatedAt, deviceId)`。

也就是说：**协议的一端（客户端）已经严格规定了「上行的是什么」，但缺了另一端**——
服务端到底应该接受什么形状的请求、应该存哪些列、增量同步靠什么游标推进、
以及多设备并发写入时如何避免互相覆盖。

在这个缺口上，有三个具体问题必须一次性定死：

1. **形状问题**：服务端收到的请求体里，除了密文还可能混进什么？
   如果服务端只是「把 JSON 存下来」，那么客户端的一个 bug（或恶意构造）
   就能让明文落进服务端数据库——**这会让「端到端加密」名存实亡**。

2. **游标问题**：增量同步需要「上次之后变了什么」。
   本地存储用的是 `updatedAt` + `version` + `deviceId` 三元组，
   但服务端**不该**存 `deviceId`（那是设备标识，属于索引明文列，见 ADR-006），
   那么增量游标到底用什么？

3. **并发问题**：多台设备可能同时上传同一条记录的不同版本。
   服务端若「后到者覆盖先到者」，就会出现**回滚**——
   一台时钟不准的旧设备把新密文覆盖成旧密文，数据静默丢失。

此外还有一个**部署现实**：
同步服务是用户自托管的（PRD AS-7），必须能在 NAS / VPS / 内网三种场景下
用最少的依赖跑起来，并且**不能**因为「数据库文件损坏」而丢掉用户的数据。

---

## 决策

### 1. 服务端只接受 `EncryptedBlob` 的 10 个字段，其余一律拒绝

请求体的顶层字段**白名单**固定为：

```
id / entityType / entityId / ciphertext / iv / tag / algorithm / keyVersion / updatedAt / version
```

与 `packages/core/src/models/encrypted-blob.ts` 的 `EncryptedBlob` **严格一一对应**。
出现白名单之外的任何字段 → **400**。

### 2. 明文字段黑名单**递归**扫描，命中即 400 且绝不落盘

除了白名单，还有一张**明文字段黑名单**：

```
amount / amountMinor / counterparty / categoryId / localDate / occurredAt / direction /
note / title / body / content / password / salt / dek / masterKey / wrappedDek /
recoveryCode / plaintext
```

检查是**递归**的——明文字段藏在嵌套对象或数组里同样被拒。
这样即便有人改写了客户端，让它把明文塞进 `meta.amount`，服务端也会挡住。

**关键实现约束**：黑名单检查发生在**任何写库动作之前**，
被拒绝的请求**不产生任何落盘副作用**（有单测断言库中行数不变）。

### 3. 服务端不校验「密文是否真的是密文」——它没有密钥，只能校验**形状**

服务端可以检查字段名、类型、长度、算法标识，但**无法**验证 `ciphertext` 是否是
某个合法明文的 AES-GCM 输出（验证需要 DEK，而服务端永远不会有 DEK）。

因此本 ADR 把服务端的能力**如实收窄**为「形状校验」：

| 服务端会拒绝 | 服务端无法判断 |
| --- | --- |
| 明文字段名（含嵌套） | `ciphertext` 里装的是不是真密文 |
| 白名单外的字段 | 密文与 `entityId` 是否真的对应 |
| 缺字段 / 类型错 / 超长 | 密文是否被篡改（GCM 标签由客户端验） |

这不是缺陷，而是**端到端加密的必然结果**：验证权与解密权一起留在客户端。

### 4. 增量游标用 `(updated_at, id)` 复合游标，不用 `seq` 自增列

服务端**不分配自增序号**。理由：自增序号会暴露「这条记录是你第几条上传的」
这类与服务端无关的顺序信息，且让服务端承担了「谁先谁后」的裁决责任。

游标改为 **`(updated_at, id)`**：

- `updated_at` 来自客户端的 `EncryptedBlob.updatedAt`，服务端**归一化**成
  `YYYY-MM-DDTHH:mm:ss.sssZ` 定宽 UTC 格式——这样**字典序等于时间序**，
  SQL 里可以直接做字符串比较，索引也能命中；
- `id` 作为同一时刻内的**次级排序键**，避免「同一毫秒的多条记录被整批跳过」。

API 上体现为 `since` + `sinceId` **一对**游标：

```http
GET /v1/blobs?since=2026-01-01T00:00:00.000Z&sinceId=<上一页最后一条的 id>&limit=100
```

响应同时返回 `nextSince` 与 `nextSinceId`，客户端原样回传即可无缝续拉。

### 5. 幂等 upsert + 版本仲裁：同一 `id` 永远只有一条记录

`id` 是主键，重复提交**不会**产生重复记录。写入时按版本仲裁：

| 提交 vs 库中 | 结果 | `status` |
| --- | --- | --- |
| 库中无此 id | 新建 | `created` |
| 提交版本 > 库中版本 | 覆盖 | `updated` |
| 版本相同且内容完全一致 | 不动 | `unchanged` |
| 版本相同但内容不同 | 覆盖 | `updated` |
| 提交版本 < 库中版本 | **忽略，保留较新的密文** | `stale` |

**为什么要有 `stale`**：多设备并发下，一台离线很久的设备醒来后会把
**旧版本**重新上传。若服务端无条件接受，就会把新密文回滚成旧密文——
这是**静默的数据丢失**，比报错严重得多。服务端不做内容合并
（它没有明文，合并不了），但**可以拒绝明显更旧的写入**。

注意：服务端只做**版本层面的仲裁**，**字段级合并仍在客户端完成**
（`packages/core/src/services/sync/merge.ts` 的三方合并）。
服务端永远不接触明文，因此永远不可能参与内容级冲突解决。

### 6. 数据库只有一张表 `encrypted_blob`，没有任何明文列

```sql
CREATE TABLE encrypted_blob (
  id            TEXT    PRIMARY KEY,
  entity_type   TEXT    NOT NULL,
  entity_id     TEXT    NOT NULL,
  ciphertext    TEXT    NOT NULL,
  iv            TEXT    NOT NULL,
  tag           TEXT    NOT NULL,
  algorithm     TEXT    NOT NULL,
  key_version   INTEGER NOT NULL,
  updated_at    TEXT    NOT NULL,
  version       INTEGER NOT NULL
);
CREATE INDEX idx_encrypted_blob_updated_at ON encrypted_blob (updated_at, id);
```

- **没有**业务明文列（金额 / 方向 / 对方 / 备注 / 分类）；
- **没有**本地存储那 7 个索引明文列（ADR-006）——服务端连「哪天有消费」都看不到；
- **没有**令牌表——令牌由环境变量注入，不入库。

### 7. 存储用 Node 22 内置 `node:sqlite`，不引入任何 npm 依赖

同步服务是**零第三方依赖**的：HTTP 用 `node:http`，数据库用 `node:sqlite`，
密码学**根本不需要**（服务端不加密也不解密）。

选择内置模块而非 `better-sqlite3` 的理由：

- 免原生模块编译链（NAS / ARM / 交叉编译场景的常见坑）；
- 免供应链风险（仓库的 X-06 红线要求依赖树干净）；
- Node 官方维护，升级随 Node 走。

### 8. 设备级授权：令牌来自环境变量，进程内只留 SHA-256 摘要

- 令牌**只**来自 `LIFEHUB_SYNC_TOKENS`（内联）或 `LIFEHUB_SYNC_TOKEN_FILE`（文件）；
- **不硬编码、不入库、不落日志**；进程内只保留 SHA-256 摘要；
- 比对用 `crypto.timingSafeEqual`，防时序攻击；
- **未配置令牌时服务拒绝启动**（fail-closed），绝不退化成「匿名可写」。

### 9. 快照用 SQLite 在线备份 API，保留 N 份

备份用 `node:sqlite` 的 `backup()`（在线备份 API），**服务运行中也能安全备份**，
不会拿到半截的 WAL 文件。快照按时间命名并滚动保留 N 份（默认 7）。

## 备选方案与不选原因

| 备选 | 不选原因 |
| --- | --- |
| **服务端直接存整个 JSON 请求体** | 明文字段一混进去就落盘，「端到端加密」名存实亡 |
| **只做白名单、不做黑名单** | 白名单已经能挡住未知字段，但**报错信息不精确**：用户会看到「未允许的字段：meta」而不是「拒绝明文字段：amount」，难以定位问题 |
| **只做黑名单、不做白名单** | 黑名单是黑名单，挡不住**将来新增**的明文字段；白名单是白名单，能挡住一切未知的未来字段。两者**同时**做才完整 |
| **只检查顶层字段，不递归** | 明文藏进 `meta.amount` 就能绕过 |
| **服务端也存 `deviceId` 以便做完整合并** | `deviceId` 是本地索引明文列（ADR-006），同步载荷明确不含它；且服务端**没有明文**，拿到 `deviceId` 也合并不了内容 |
| **服务端分配自增 `seq` 做游标** | 暴露服务端侧的顺序信息；且让服务端承担「谁先谁后」的裁决责任，与「服务端只是密文中转站」的定位冲突 |
| **用 `updated_at` 单字段做游标** | 同一毫秒的多条记录会被整批跳过，**静默丢数据**；必须加 `id` 次级键 |
| **用整数毫秒时间戳存 `updated_at`** | 可读性差（排查问题时看不懂库里的数字），且与客户端的 ISO 8601 表示不一致，徒增转换层 |
| **服务端无条件接受上传（last-write-wins）** | 离线设备会把新密文回滚成旧密文，**静默数据丢失**；版本仲裁能挡住这一类 |
| **服务端做内容级合并（保留两边）** | 服务端没有明文，**物理上做不到**；且这会迫使服务端接触明文，直接违反红线 |
| **用 `better-sqlite3` 等原生模块** | 需要编译链，NAS / ARM 场景易翻车；且违反「零 npm 依赖」的供应链红线 |
| **用 Express / Fastify 等框架** | 引入依赖树；`node:http` 对 5 个端点完全够用，框架带来的抽象收益远小于供应链成本 |
| **令牌存进数据库做多用户管理** | 令牌落库 = 密钥材料落盘，与「服务端不存密钥材料」的红线冲突；自托管单用户场景也不需要 |
| **用固定字符串做 Bearer token** | 会被日志、代理、shell 历史记录泄露；随机 32 字节 + SHA-256 摘要驻留内存更安全 |
| **令牌明文驻留内存并直接比较** | 内存转储即泄露令牌；`timingSafeEqual` + 摘要比较可同时防内存泄露与时序攻击 |
| **未配置令牌时允许匿名访问** | 一次配置疏漏就等于把服务开成公共写入接口；**失败即关闭**是唯一安全的选择 |
| **删除时留墓碑（tombstone）** | 正确但需要协议层配套（见「后果」），本轮未实现；已记入 `docs/roadmap.md` 阶段 5 前置提醒 |
| **快照直接 `cp` 数据库文件** | WAL 模式下 `cp` 会拿到**半截数据**；必须用在线备份 API |

## 后果

### 正面

- **「服务端只见密文」从口号变成可执行断言**：白名单 + 递归黑名单 + 单测断言库中行数，
  三层机制共同保证明文**不会**落盘。
- **数据库泄露等于零损失**：库里只有密文与元信息，**没有**任何业务明文列。
- **增量同步不漏数据**：`since` + `sinceId` 复合游标覆盖了「同一毫秒多条」这个
  最容易出错的边界情况。
- **多设备并发不回滚**：`stale` 仲裁挡住了离线设备的旧版本覆盖。
- **部署极简**：零 npm 依赖、`node:http` + `node:sqlite`，NAS / VPS / 内网三种场景
  用同一个镜像与同一份 compose 即可。
- **可运维**：在线快照 + 保留份数 + `docker compose` 内置夜间任务，数据不会因为
  一次容器重建而丢失。

### 负面 / 代价

- **服务端能看到元信息**：记录条数、每条多长、什么时间改的、属于哪个实体类型与实体 id。
  这些是同步协议必需的，但确实是**用户可感知的信息暴露**，已在
  `apps/sync-server/README.md` §2「能力边界」中**如实披露**。
- **删除没有墓碑**：A 端删除后 B 端不会自动感知，两端可能短暂不一致。
  这是**已知缺口**，必须留到阶段 5 与协议一起补齐。
- **服务端不做内容级合并**：同一字段的双端并发修改，只能由客户端重新拉取后
  在本地用 `merge.ts` 解决。客户端的同步逻辑因此更复杂。
- **`updatedAt` 的时钟依赖**：客户端设备时钟不准会导致增量游标异常
  （未来时间的记录可能长期拉不到）。这与 ADR-002 的时间假设同源，
  属于「用户设备时钟基本准确」这一已声明前提（AS-8）。
- **`node:sqlite` 在 Node 22 仍是实验特性**：启动时会打印 `ExperimentalWarning`，
  且未来 API 可能变化。需要锁定 Node 版本（`.nvmrc` = 22）。

### 需要注意的坑

- **不要给 `updated_at` 存非定宽格式**：字典序必须等于时间序，
  否则增量拉取会漏数据。服务端统一归一化为 `YYYY-MM-DDTHH:mm:ss.sssZ`。
- **不要把 `since` 和 `sinceId` 只传一个**：只传 `since` 会跳过同一时刻的其余记录。
- **不要为了「方便排查」在服务端加明文字段**：哪怕是「可选的明文字段」
  也会让整个安全叙事崩塌。
- **不要把令牌写进 compose 文件或 Dockerfile**：用环境变量或 Docker Secret。
- **快照必须复制到另一块盘**：同一块盘上的备份会与数据一起消失。

## 关联需求

- **X-01 ④**：同步载荷 / 备份只含密文——服务端侧的白名单与黑名单是其镜像约束。
- **X-11**：冲突合并基础——字段级合并在客户端完成，服务端只做版本仲裁。
- **X-12**：自托管同步服务——本 ADR 固定其协议、存储与授权形态。
- **X-13**：多设备授权——设备级 Bearer 令牌是其服务端形态。
- **AS-7**：同步服务由用户自托管，运营方不承担可用性承诺。
- **R5**：同步载荷与备份只含密文。
- **NF-S-1**：存储层检索不到任何明文业务数据。
