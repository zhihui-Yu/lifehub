# ADR-002 · 时间与时区：ISO 8601 UTC + localDate 双时间戳

| 项 | 值 |
| --- | --- |
| **状态** | 已采纳（Accepted） |

| **决策者** | 主理人 / 架构师 / 工程师 |
| **关联需求** | A-04 ③、A-05、A-09 ①、A-11、NF-P-1、R9 |

---

## 背景

账单 CSV 里的日期格式五花八门：

| 来源 | 典型写法 |
| --- | --- |
| 微信支付 | `2024-01-15 08:30:00`（无时区） |
| 支付宝 | `2024-01-15`（纯日期） |
| 银行导出 | `2024/01/15`、`15/01/2024`（欧式） |
| Excel | `45306`（序列号） |
| 手工整理 | `20240115`、`2024年1月15日` |

同时存在**两个时间视角**的冲突：

1. **绝对时刻**：这笔交易发生在什么时间点（跨设备同步、排序、增量拉取都依赖它）；
2. **日历日**：用户认为这笔交易属于「哪一天」（账单分组、月度统计依赖它）。

这两者**不是一回事**：UTC `2024-01-15T20:30:00Z` 在 `Asia/Shanghai` 是 **1 月 16 日**。
如果只存一个字段，必然有一头出错——按 UTC 截前 10 位会让晚上 8 点后的消费被算到第二天，
按本地时间存则跨设备排序与同步全都乱掉。

---

## 决策

### 1. 双时间戳：`occurredAt`（绝对时刻）+ `localDate`（日历日）

```ts
export interface Bill extends BaseEntity {
  occurredAt: string;    // ISO 8601 UTC，形如 '2024-01-15T08:30:00.000Z'
  localDate: string;     // 用户时区下的日历日，形如 '2024-01-15'
  sourceTimeZone: string;// 来源时区标识，如 'Asia/Shanghai'
  // ...
}
```

- **`occurredAt` 是唯一事实来源**：排序、增量同步、冲突合并都用它。
- **`localDate` 是派生值**：由 `occurredAt` + 用户时区算出，供分组与月统计使用。
- **`sourceTimeZone` 记录来源时区**：当源文件是「本地时间」时，需要知道它指的是哪个时区。

### 2. 存储与传输一律 ISO 8601 UTC

- 落盘、序列化、同步载荷中的时间戳统一为 `...Z` 结尾的 UTC 字符串；
- 校验用 `ISO_UTC_PATTERN`（`packages/core/src/constants.ts`）；
- **不存**本地时间字符串，**不存** Unix 时间戳数字（字符串可读、可字典序比较、跨端无歧义）。

### 3. 核心层不直接调用 `Date.now()`

统一走 `Clock` 端口：

```ts
export interface Clock {
  now(): Date;
  nowIso(): string;
}
```

这让时间相关的逻辑**可测试**（测试注入 `FixedClock`，断言时间戳精确相等），
也让未来 Flutter 端可以用 `DateTime.now().toUtc()` 实现同一接口。

### 4. 解析策略：显式优先、逐级回退

`parseFlexibleDate()` 的回退顺序：

1. **ISO 8601**（带或不带时区偏移）；
2. **已知格式表**（`DATE_FORMATS`：含毫秒 / 不含毫秒、斜杠 / 横杠 / 点号分隔、纯日期、时间在��）；
3. **Excel 序列号**（`isExcelSerialDate` → `excelSerialToDate`，纪元为 1899-12-30）；
4. **紧凑格式**（`20240115`）；
5. 都不匹配 → 抛 `LIFEHUB_E_DATE_INVALID`。

**无时区的日期按 UTC 解释**，随后仍按用户时区重算 `localDate`——
这样「用户填的本地时间」不会因为跨时区被平移到别的日子（系统设计 §1.2 难点 1）。

### 5. 用户时区可配置，默认 `Asia/Shanghai`

`AppSettings.userTimeZone`，取值经 `assertTimeZone()` / `isValidTimeZone()` 校验；
`TIMEZONE_CANDIDATES` 提供候选项。**服务端（同步服务）不参与时区推断**——
时间戳已经是 UTC，不需要服务端知道用户在哪。

## 备选方案与不选原因

| 备选 | 不选原因 |
| --- | --- |
| **只存本地时间字符串**（`2024-01-15 08:30:00`） | 跨时区设备同步后会互相覆盖；排序在不同 locale 下结果不同；无法表达「这是哪一刻」 |
| **只存 UTC 时间戳，运行时再算 localDate** | 列表页要在客户端解密后对每行做时区换算，10 万行时明显拖慢首屏；而且导出给第三方时缺少用户视角的日期 |
| **存 Unix 时间戳数字** | 可读性差、调试困难、跨语言时区处理易错 |
| **存本地日期 + 本地时间两个独立字段** | 两份数据可能互相矛盾（谁说了算？），且仍无法表达绝对时刻 |
| **在服务端做时区转换** | 服务端只见密文，**根本不知道**用户时区；这与「服务端零业务语义」直接冲突 |
| **核心层直接调用 `Date.now()`** | 时间相关逻辑无法确定性测试；跨端实现差异（秒 / 毫秒精度）难以对齐 |

## 后果

### 正面

- **排序与同步有唯一依据**：`occurredAt` 字典序即时间序，跨设备、跨时区结果一致。
- **分组与统计符合直觉**：`localDate` 直接可用，用户看到的「1 月 15 日」就是他记的那天。
- **解析可测试**：`FixedClock` + 固定输入 → 固定输出，不受运行时刻影响。
- **格式自描述**：ISO 8601 带 `Z`，任何人（包括未来的 Dart 端）都能无歧义解析。

### 负面 / 代价

- **每个账单多存两个字符串**：`occurredAt` + `localDate`，10 万行约多占 3 MB（可接受）。
- **时区知识必须在客户端**：用户改了时区，历史账单的 `localDate` 会随之变化（这是**期望行为**，
  但要理解「1 月 15 日的支出」在换时区后可能变成 1 月 16 日）。
- **解析器要覆盖多种格式**：`DATE_FORMATS` 表需要持续维护；遇到新格式要加一条。

### 需要注意的坑

- **不要用 `occurredAt.slice(0, 10)` 当 `localDate`**：那是 UTC 日期，不是用户日历日。
  正确做法是 `toLocalDate(instant, timeZone)`。
- **无时区的输入按 UTC 解释**是有意为之（避免「本地时间当 UTC」的跨天偏差），
  但对「用户手动输入当地时间」的账单会有最多 ±1 天的偏差风险；
  用户可在导入时指定 `sourceTimeZone` 修正。
- **`localDate` 是索引明文列**（ADR-006），只暴露「哪天有消费」，不暴露「买了什么、花了多少」。

## 关联需求

- **A-04 ③**：CSV 日期格式需兼容多种写法并正确落到 `occurredAt` / `localDate`。
- **A-05**：列映射把「日期」列映射到 `occurredAt` 语义字段。
- **A-09 ①**：账单按 `localDate` 分组展示。
- **A-11**：单行解析失败（日期非法）时记入 `ImportSummary.errors` 并跳过该行。
- **NF-P-1**：解析性能受日期格式回退链影响，故用「显式优先 + 逐级回退」并对常见格式做快路径。
- **R9**：时间格式与系统设计 §8.2 一致。
