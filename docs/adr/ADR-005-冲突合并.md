# ADR-005 · 冲突合并：三方合并 + (updatedAt, deviceId) 决胜

| 项 | 值 |
| --- | --- |
| **状态** | 已采纳（Accepted） |
| **日期** | 2026-10-30 |
| **决策者** | 主理人 / 架构师 / 工程师 |
| **关联需求** | X-11 ①②③、X-13、NF-PR-4 |

---

## 背景

多设备场景下，同一条账单可能被两台设备**离线**修改：

```
设备 A（本地）：备注改成「拿铁大杯」
设备 B（远端）：备注改成「拿铁 大杯 + 燕麦」
```

同步时服务端只是「密文中转站」，**不做合并**（它连密文都解不开）。
因此合并必须发生在**客户端**，且必须满足一个硬性要求：

> **合并结果与两条记录的到达顺序无关**（PRD X-11 ③）。

否则会出现「先同步 A 再同步 B 得到 X，先同步 B 再同步 A 得到 Y」的**不确定性**——
用户在设备 A 上看到的内容与设备 B 不同，且每次同步都可能翻转，**不可复现、不可审计**。

---

## 决策

### 1. 三方合并（Three-way Merge）

```ts
mergeRecord<T extends MergeableEntity>(
  local: T | null,   // 本地实体；本地不存在时传 null
  remote: T,         // 远端实体
  base: T | null,    // 上次同步后的共同祖先快照；首次同步时传 null
): MergeResult<T>
```

规则表：

| local vs base | remote vs base | 结果 | 是否冲突 |
| --- | --- | --- | --- |
| 相同 | 相同 | 保留 base | 否 |
| 不同 | 相同 | 取 local | 否 |
| 相同 | 不同 | 取 remote | 否 |
| 不同 | 不同（值相等） | 取该值 | 否 |
| 不同 | 不同（值不等） | **LWW：`(updatedAt, deviceId)` 大者胜** | 是 |

- **只有一端改了某个字段** → 直接采纳那一端，不算冲突（这是三方合并相对「整条记录 LWW」的最大价值：
  两端改不同字段时**两个改动都保留**）。
- **两端改成同一个值** → 不算冲突。
- **两端改成不同的值** → 才是真冲突，按决胜键处理并记入 `conflicts`。

### 2. 决胜键：`(updatedAt, deviceId)` 字典序比较

```ts
function compareRecency(left, right): number {
  if (left.updatedAt !== right.updatedAt) {
    return left.updatedAt > right.updatedAt ? 1 : -1;
  }
  if (left.deviceId !== right.deviceId) {
    return left.deviceId > right.deviceId ? 1 : -1;
  }
  return 0;
}
```

- `updatedAt` 是 ISO 8601 UTC 字符串，**字典序即时间序**；
- 时间相同时用 `deviceId` 兜底——`deviceId` 是本地生成的 UUIDv7，**全局唯一且与设备无关**，
  保证「同一时刻的两端修改」也有确定结果；
- 这个比较**与到达顺序无关**，因此双端并发修改能确定性收敛。

### 3. `FieldConflict` 同时记录「胜方位置」与「胜方设备」

```ts
export interface FieldConflict {
  field: string;
  localValue: string;
  remoteValue: string;
  winner: 'local' | 'remote';   // 位置相关：入参对调后会翻转
  winnerDeviceId: string;        // 顺序无关：跨设备一致性断言的依据
}
```

- `winner` 是**位置标签**，把入参对调后必然翻转，**不能**用来断言「结果与顺序无关」；
- `winnerDeviceId` 才是**与顺序无关**的表达——它记录的是「哪台设备赢了」，
  无论 A 先到还是 B 先到，胜方设备都是同一个。

> 这一条是本轮测试修正的核心：早期实现只有 `winner`，导致「确定性」用例无法正确表达。

### 4. 元字段单独处理，不参与字段级冲突

`id` / `version` / `updatedAt` / `deviceId` 不进字段级冲突表：

- `id` 取本地值；
- `version` 取 `Math.max(local.version, remote.version, base.version) + (changed ? 1 : 0)`，**单调递增**；
- `updatedAt` / `deviceId` 取**胜方**（较新者）的值。

### 5. 无 base 时退化为整条记录 LWW

首次同步（没有共同祖先）时无法做字段级判断，退化为「整条记录取较新者」，
并把**所有差异字段**记入 `conflicts`（供 UI 展示，不阻塞同步）。

## 备选方案与不选原因

| 备选 | 不选原因 |
| --- | --- |
| **服务端做合并** | 服务端只见密文，**无法解密也无法比较字段**；这与「服务端零业务语义」直接冲突 |
| **最后写入者胜出（LWW，按到达时间）** | 结果**依赖到达顺序**，不满足 X-11 ③；且「到达时间」会被网络延迟污染 |
| **按 `updatedAt` 单字段决胜** | 同一毫秒内的两次修改仍会翻转；必须加 `deviceId` 兜底才能保证确定性 |
| **整条记录 LWW（不做字段级合并）** | 两端改**不同字段**时会丢失其中一端的改动（例如 A 改备注、B 改分类） |
| **人工冲突解决 UI**（让用户每次都选） | 同步是后台行为，不能阻塞；且冲突可能大量出现，体验不可接受 |
| **向量时钟 / CRDT** | 正确但复杂度高：需要维护每条记录的版本向量，存储与实现成本都远超个人工具场景；本期目标是「确定性收敛」，CRDT 解决的是「无冲突合并」 |
| **用 `deviceId` 单字段决胜** | `deviceId` 与「谁更新」无关，语义错误 |
| **用 `createdAt` 决胜** | 创建时间与修改时间无关，语义错误 |

## 后果

### 正面

- **确定性收敛**：无论同步顺序如何，两端最终得到**同一个结果**（单测断言 `winnerDeviceId` 相等）。
- **不丢改动**：两端改不同字段时两个改动都保留（三方合并的核心价值）。
- **冲突可审计**：`conflicts[]` 记录了每个冲突字段的两侧取值与胜方，可展示给用户。
- **版本号单调递增**：合并结果的 `version` 严格大于两端，冲突合并不会造成版本回退。
- **实现简单**：约 170 行，无额外依赖，无 CRDT 的状态膨胀。

### 负面 / 代价

- **需要保存共同祖先**：客户端必须保留「上次同步后的快照」才能做三方合并——
  这需要额外的存储（可以是同步时记录的 base 副本，或服务端返回的 `baseVersion`）。
  **本期只落合并算法与单测，同步协议（S5）尚未实现**。
- **整数字符串序依赖时间戳精度**：`updatedAt` 精确到毫秒；同一毫秒内用 `deviceId` 兜底。
- **`conflicts` 只报告不阻断**：本轮策略是「自动按决胜键合并 + 记录冲突」，没有提供「让用户逐条选择」的 UI
  （未来 A-11 风格的冲突面板是阶段 5 的增量）。
- **字段级比较需要稳定的字段顺序**：当前实现按 `Object.keys` 顺序遍历，
  字段顺序不同不影响结果（因为每个字段独立判断），但**元字段被排除**的规则必须稳定。

### 需要注意的坑

- **不要用 `winner` 断言确定性**：它是位置相关的标签。要断言「与顺序无关」，
  请断言 `winnerDeviceId`（或断言 `merged` 的内容相等）。
- **`local` / `remote` 的语义**：调用方必须保证「local 是本设备当前值、remote 是刚从服务端拉到的值」。
  参数对调会翻转 `winner`，但**不会**翻转 `winnerDeviceId` 与 `merged`。
- **删除没有墓碑语义**：本轮没有实现「删除 vs 修改」的冲突处理
  （删除需要墓碑标记 + 保留期），同步协议实现时必须补上。

## 关联需求

- **X-11 ①**：三方合并基础算法。
- **X-11 ②**：字段级差异检测与冲突记录。
- **X-11 ③**：LWW 决胜且**结果确定、不依赖设备执行顺序**。
- **X-13**：多设备授权（阶段 5；`deviceId` 已在模型中预留）。
- **NF-PR-4**：离线优先的最终一致性。
