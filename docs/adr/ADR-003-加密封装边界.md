# ADR-003 · 加密封装边界：主密钥包裹 DEK，恢复码直接包裹 DEK

| 项 | 值 |
| --- | --- |
| **状态** | 已采纳（Accepted，含「恢复码可解包 DEK」设计增量） |
| **日期** | 2026-10-30 |
| **决策者** | 主理人 / 架构师 / 工程师 |
| **关联需求** | A-07、X-03、X-04、X-10、NF-S-1～NF-S-4、NF-PR-6、R3、R4、R5 |

---

## 背景

端到端加密要同时满足四个相互拉扯的目标：

1. **用户数据不可读**：落盘与上传的都是密文；
2. **改口令代价可控**：不能因为改一次密码就重写全部存量密文；
3. **可恢复**：用户忘主密码时，靠恢复码能找回数据；
4. **零落盘密钥**：不存口令哈希、不存任何可离线爆破的派生值。

第 2 条与第 1 条天然冲突：如果主密钥直接加密业务数据，改口令就必须「解密全部 → 换密钥 → 重加密全部」，
中途失败会留下半新半旧的密文库；数据量越大风险越高。

第 3 条则暴露了一个**容易被设计错的陷阱**：早期版本让「恢复码派生出主密钥」，
但恢复码与主口令是**两个不同的字符串**，用同一套 KDF 参数派生出来的密钥**根本不是同一把**——
恢复路径在设计上就不成立。

---

## 决策

### 1. 双层密钥结构：主密钥 → 包裹 → DEK → 加密 → 业务密文

```
用户口令 ──scrypt(N=2^15, r=8, p=1)──► 主密钥 masterKey
                                            │ AES-GCM 包裹（AAD: vaultParams|dek|keyVersion）
                                            ▼
                                          DEK（32 字节，仅驻留内存）
                                            │ AES-GCM 加密（AAD: entityType|entityId|keyVersion）
                                            ▼
                                          业务密文
```

- **主密钥只做一件事：包裹 DEK**。改口令 = 重包裹 DEK + 用 DEK 重加密存量密文，密钥材料本身不变。
- **DEK 只驻留内存**，锁定时 `fill(0)` 擦除（NF-S-2）；**永不上传**。
- `VaultParams.currentDek` / `previousDek` 存的是**被包裹的** DEK（A-07 ②：落盘无任何明文密钥）。

### 2. 不存储口令哈希：用哨兵密文校验口令（A-07 ⑦）

```ts
const verifier = await this.crypto.encryptRecord(
  masterKey, 'vaultParams', VAULT_VERIFIER_ID, keyVersion, VAULT_VERIFIER_PLAINTEXT,
); // 明文为 'lifehub:verify:v1'
```

解锁时解密哨兵并比对明文。落盘的是**密文**，不是口令哈希、不是口令派生值——
即便数据库泄露也无法离线爆破口令（scrypt 的成本在攻击端同样要付，但没有 salt + 次数的组合可离线复用）。

### 3. AAD 绑定实体身份，阻断「密文搬移」

- 业务密文 AAD = `entityType + ' ' + entityId + ' ' + keyVersion`；
- DEK 包裹 AAD = `'vaultParams' + ' ' + 'dek' + ' ' + keyVersion`。

把 A 记录的密文搬到 B 记录上会 GCM 认证失败。恢复码解包 DEK 时也走同一条 AAD 规则。

### 4. 恢复码 = 一把「恢复 DEK」的备用钥匙（**主理人批准的设计增量**）

```
恢复码 ──scrypt(独立盐值, 独立 KDF 参数)──► 恢复密钥
                                              │ AES-GCM 包裹 DEK
                                              ▼
                                    wrappedDek（落盘，与主密钥包裹的是同一把 DEK）
```

- `RecoveryMeta` 扩展为：`id / checksum / exported / createdAt` + `salt` + `kdfParams` + `wrappedDek`；
- 解锁流程：**校验 checksum**（`sha256(恢复码 + 恢复盐值)`）→ 用恢复盐值与恢复 KDF 参数派生恢复密钥
  → 解包 `wrappedDek` 取得**真正的 DEK**；
- **恢复码明文绝不落库**（X-03 ⑤）——本地只存 checksum、恢复盐值、恢复 KDF 参数与被包裹的 DEK；
- **重新生成恢复码**：换新的恢复盐值 / KDF 参数 / 包裹密钥，用**同一把 DEK** 重新包裹 →
  旧恢复码的 checksum 与包裹内容同时失效。

> 恢复码与口令派生的主密钥**相互独立**：恢复码泄露不影响口令安全，反之亦然。

### 5. 加密能力一律走 `CryptoProvider` 端口

核心层不出现 `crypto.subtle` / `node:crypto`，只依赖端口接口；
实现有 `WebCryptoProvider`（浏览器）、`NodeCryptoProvider`（Node）、`NobleCryptoProvider`（兜底）。
这保证 §6.2 要求的「可移植边界」——Flutter 端可换成 `dart:ffi` 调用平台原生实现。

### 6. 备份与同步只搬运密文，不含密钥

- 备份文件结构只有 `magic / version / exportedAt / algorithm / keyVersion / blobs`；
- **不含**盐值、DEK、主密钥，也**不含**索引明文列；
- 同步载荷的 blob 字段白名单由 `SYNC_BLOB_ALLOWED_FIELDS` 固定，静态 + 运行时双重断言。

## 备选方案与不选原因

| 备选 | 不选原因 |
| --- | --- |
| **主密钥直接加密业务数据** | 改口令必须全量解密 + 重加密，中断即产生半新半旧的密文库；数据量越大越危险 |
| **用口令哈希（bcrypt / argon2）校验口令** | 哈希落盘 = 可离线爆破；scrypt 派生值落盘同理。哨兵密文方案把「校验」变成「解密」，攻击端也要付满 KDF 成本且无法复用 |
| **恢复码派生出主密钥**（早期设计） | 恢复码与主口令是不同字符串，派生结果**不是同一把密钥**，恢复路径在设计上不成立（已被测试证伪） |
| **恢复码 = 第二个口令，共用保险库盐值与 KDF 参数** | 恢复码强度远低于口令（助记码熵有限），与主口令共用盐值会让弱口令的离线爆破成本被摊薄 |
| **用 RSA / 公私钥对（口令加密私钥）** | 多一层密钥管理复杂度；口令变更不影响密钥这一点用「包裹 DEK」已经解决；且 RSA 无 AEAD 语义 |
| **把 DEK 直接落盘** | 数据库泄露即数据泄露，违背 E2EE 的全部前提 |
| **加密服务放在服务端** | 与「服务端只见密文」直接冲突；用户不接受信任第三方托管密钥（AS-4） |
| **在核心层直接调用 `crypto.subtle`** | 破坏零 DOM 约束与跨端可移植性 |

## 后果

### 正面

- **改口令的实现成本可控**：只需重包裹 + 重加密存量密文，且 DEK 本身不变。
- **恢复路径在密码学上真正成立**：恢复码解包的是**同一把 DEK**，解出来的就是用户的数据。
- **落盘无任何明文密钥**：盐值与被包裹的 DEK 都是公开参数，哨兵是密文。
- **「密文搬移」攻击被 AAD 阻断**。
- **可移植**：加密全部经由端口，Flutter 端换实现即可。

### 负面 / 代价

- **多一层密钥层级**：理解成本与调试成本上升（要分清 masterKey / recoveryKey / DEK / 密文）。
- **口令强度直接决定主密钥强度**：弱口令 → 弱主密钥 → DEK 包裹可被离线爆破。
  因此口令强度校验（≥ 8 位 + 阻断式确认）与冷却机制（5 次失败冷却 30 秒）是硬要求。
- **恢复码强度有限**：助记码熵低于口令，因此必须用**独立的盐值与 KDF 参数**，
  且恢复码泄露的后果是「数据可被解开」，必须离线保管。
- **重新生成恢复码会作废旧码**：这是安全属性，但也意味着用户必须重新导出并保管。

### 需要注意的坑

- **`UnlockedVault.masterKey` 的语义在恢复路径下不同**：口令解锁返回口令派生的主密钥；
  恢复码解锁返回**恢复密钥**。两者都能解开 DEK 包裹，但不是同一份材料——
  在这两条路径上执行「改口令」会得到不同结果（阶段 5 的轮换实现要显式处理）。
- **审计日志写入需要正确的 DEK**：建库 / 解锁这两条审计发生在「DEK 装进 `DekProvider` 之前」时，
  会写失败或写错密钥。解决方案是 `onDekAvailable` 回调：**先装 DEK，再写审计**。
- **备份往返必须复用同一把 DEK**：备份文件按设计**不含 DEK**，
  恢复到新环境时必须用原环境的密钥，否则必然 `LIFEHUB_E_CRYPTO_AUTH_FAILED`。

## 关联需求

- **A-07 ②③⑥⑦**：口令派生参数、哨兵校验、参数版本、不存口令哈希。
- **X-03 ①②③④⑤**：恢复码生成、导出、独立盐值、重新生成使旧码失效、恢复码明文不入库。
- **X-04 ①②**：档案与密钥的本地安全存储、无明文密钥落盘。
- **X-10**：密钥轮换（阶段 5 完整实现）。
- **NF-S-1**：存储层检索不到明文业务数据。
- **NF-S-2**：密钥只驻留内存，锁定即擦除。
- **NF-S-3**：弱口令防护（强度校验 + 冷却）。
- **NF-S-4**：解密失败统一归一，不返回部分明文。
- **NF-PR-6**：备份文件不含密钥。
- **R3 / R4 / R5**：零网络出口、唯一密文写通道、载荷只含密文。
