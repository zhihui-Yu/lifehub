# ADR-004 · 存储抽象层：StorageAdapter 端口 + 两个门面

| 项 | 值 |
| --- | --- |
| **状态** | 已采纳（Accepted） |
| **日期** | 2026-10-30 |
| **决策者** | 主理人 / 架构师 / 工程师 |
| **关联需求** | X-08、X-09、A-12、NF-S-1、R1、R2、R4 |

---

## 背景

同一份领域逻辑最终要跑在三个地方：

| 端 | 存储介质 | 加密能力 |
| --- | --- | --- |
| 浏览器（本期） | IndexedDB | WebCrypto（`crypto.subtle`） |
| Node（测试 / CLI / 同步服务） | 文件 / 内存 | `node:crypto` |
| Flutter（阶段 3+） | sqflite / drift | `dart:ffi` → 平台原生 |

如果领域层直接写 `indexedDB.open(...)`，那么：

- 核心层**无法在 Node 里跑测试**（要么引入 fake-indexeddb，要么只能写浏览器端测试）；
- 核心层**违反零 DOM 红线**（R1）；
- Flutter 端**必须重写全部存储相关代码**；
- 换存储引擎（IndexedDB → SQLite）就是一次全量重写。

同时还有一个安全侧的硬要求：**存储层不得存在任何明文业务写入口**（R4）。
如果领域层能直接调 `adapter.put(entityType, 明文对象)`，这个要求就只能靠代码评审保证，无法用类型或结构强制。

---

## 决策

### 1. 定义 `StorageAdapter` 端口，核心层只依赖接口

```ts
export interface StorageAdapter {
  open(): Promise<void>;
  close(): Promise<void>;
  get(entityType: EntityType, id: string): Promise<StoredRecord | null>;
  getMany(entityType: EntityType, ids: readonly string[]): Promise<StoredRecord[]>;
  query(entityType: EntityType, filter?: StorageQueryLike): Promise<StoredRecord[]>;
  put(entityType: EntityType, record: StoredRecord): Promise<void>;
  putMany(entityType: EntityType, records: readonly StoredRecord[]): Promise<void>;
  delete(entityType: EntityType, id: string): Promise<void>;
  deleteMany(entityType: EntityType, ids: readonly string[]): Promise<void>;
  count(entityType: EntityType, filter?: StorageQueryLike): Promise<number>;
  clear(entityType: EntityType): Promise<void>;
}
```

端口**只出现在 `packages/core/src/types` 与 `packages/core/src/storage/adapter.ts`**，
实现方在 `apps/web/platform`（Dexie）与 `packages/core/src/storage/memory-adapter.ts`（测试替身）。

### 2. 存储记录的形状固定为 `StoredRecord`

```ts
export interface StoredRecord {
  id: string;
  entityType: EntityType;
  version: number;
  createdAt: string;      // ISO 8601 UTC
  updatedAt: string;      // ISO 8601 UTC
  deviceId: string;
  localDate: string | null;   // 索引明文列
  occurredAt: string | null;  // 索引明文列
  payload: EncryptedPayload | PlainPayload;
}
```

- **业务实体不进存储层**：存进去的是 `StoredRecord`，业务字段全在 `payload` 里（密文）。
- **索引明文列是 `StoredRecord` 的一部分**：范围查询与排序由适配器在**不解密**的前提下完成。

### 3. 两个门面把「写入口」收敛到两条通道

| 门面 | 允许写入的实体 | 载荷类型 | 用途 |
| --- | --- | --- | --- |
| `EncryptedStore` | 全部业务实体（`bill` / `category` / `ruleTemplate` / `importBatch` / `auditLog`） | **必须是密文** | 业务数据的**唯一**写通道（R4） |
| `PlainStore` | 仅 `vaultParams` / `recoveryMeta` / `appSettings` | 明文 JSON | 解锁前就需要读取的三类实体 |

- `EncryptedStore.put()` 内部先调 `extractMeta()` 校验实体带 `id / version / createdAt / updatedAt / deviceId`，
  缺字段直接抛 `LIFEHUB_E_VALIDATION`；
- `PlainStore.put()` 先过 `assertPlain()` 白名单校验，越权抛 `LIFEHUB_E_VALIDATION`；
- 两类实体**没有交叉的写入口**——不存在「把业务实体当明文写进去」的路径。

### 4. 领域实体与存储记录之间的转换放在仓储层

```ts
export class BillRepository {
  async put(bill: Bill): Promise<void> { /* bill → StoredRecord（含索引明文列） */ }
  async list(query?: BillQuery): Promise<Bill[]> { /* StoredRecord → bill（解密） */ }
}
```

仓储层是唯一知道「账单有哪些索引列」的地方；
`EncryptedStore` 只关心「怎么加密、怎么落盘」。

### 5. 查询在存储层做范围过滤，语义过滤在解密后做

- `StorageQueryLike.where` **只允许索引明文列**（`entityType` / `localDate` / `occurredAt` /
  `createdAt` / `updatedAt` / `version` / `deviceId`）；
- 关键词、方向、分类等**语义过滤**在解密后于内存中完成（系统设计 §5 假设 A-8）。

### 6. 测试替身与生产实现共享同一份语义

`MemoryStorageAdapter` 在内存里完成过滤、排序、分页，语义与 Dexie 实现保持一致——
因此核心层的**全部测试都在 Node 环境跑**，不需要 jsdom，也不需要 fake-indexeddb。
这既是工程效率，也是「核心层零 DOM」最直接的可执行证明（PRD A-01 ①）。

## 备选方案与不选原因

| 备选 | 不选原因 |
| --- | --- |
| **核心层直接用 IndexedDB** | 违反零 DOM 红线（R1）；Node 侧无法测试；Flutter 端必须重写 |
| **用 `localStorage` / `sessionStorage`** | 容量只有 5–10 MB 且同步阻塞；无法存二进制密文；无法做范围查询 |
| **直接用 Dexie，核心层依赖它** | 把 IndexedDB 的 API 形状泄漏进领域层；违反 R2（核心层依赖不含 Dexie） |
| **引入 fake-indexeddb 做测试** | 多一个测试依赖；测试速度与真实度都劣于内存替身；仍需 jsdom |
| **只定义一个泛型 KV 端口（`get/set`）** | 无法表达「按索引列范围查询」；上层被迫把过滤逻辑下推到存储层，破坏分层 |
| **允许领域层直接写 `adapter.put()`** | 存在明文业务写入口，R4 无法强制；且加密逻辑会散落到各处 |
| **把加密下沉到适配器** | 适配器就绑死了密码学实现，跨端移植无从谈起；加密策略属于领域层关注点 |
| **用 SQLite（better-sqlite3）做 Web 端存储** | 需要 WASM 化的 sqlite3，体积与兼容性成本高于 Dexie；本期无收益 |

## 后果

### 正面

- **核心层可在任何环境跑**：Node 测试无 jsdom、无浏览器依赖，CI 快且稳。
- **跨端移植有明确落点**：Flutter 端实现同一个 `StorageAdapter` 即可。
- **写入口收敛**：明文业务数据**无处可写**（R4 由类型 + 门面结构 + 静态扫描三重保证）。
- **查询性能可控**：范围过滤在存储层完成，10 万行不需要全量解密。
- **可替换存储引擎**：IndexedDB → SQLite / 文件，是换实现而不是改领域层。

### 负面 / 代价

- **多一层映射代码**：领域实体 ↔ `StoredRecord` 的转换在每个仓储里都要写一遍，样板代码偏多。
- **索引列要手工维护**：新增实体时必须同步确定索引列，否则范围查询失效——
  这是**有意保留的摩擦**：索引列是隐私边界，不能自动生成。
- **端口方法较多**（11 个）：实现适配器的工作量不小，但换来了语义一致性。
- **`StoredRecord` 的字段是"半明文"**：初学者容易误以为明文可以直接塞进 `payload`；
  靠 `PlainStore` 白名单与 `EncryptedStore` 的强校验来防。

### 需要注意的坑

- **实体类型与存储表名绑定**：`put()` 会校验 `record.entityType === entityType`，不一致抛 `LIFEHUB_E_STORAGE`。
- **审计日志的领域模型没有存储元字段**：`AuditLog` 只有 6 个业务字段，
  而 `EncryptedStore` 要求 5 个存储元字段——由 `AuditLogRepository.save()` 在**落库环节**补齐
  （领域模型保持不变，见 ADR-006 的说明）。
- **恢复备份时索引列为 `null`**：`createRestoredStoredRecord()` 统一置 `null`（语义是「未知」），
  恢复后需要重新索引才能按日期范围查询。

---

## 关联需求

- **X-08**：存储抽象层，核心层不感知具体存储实现。
- **X-09**：索引明文列与范围查询能力。
- **A-12**：幂等导入依赖 `ImportBatch` 的文件哈希索引查询。
- **NF-S-1**：存储层检索不到明文业务数据。
- **R1**：核心层零 DOM（由端口抽象保证）。
- **R2**：核心层依赖不含 Dexie / React / MUI。
- **R4**：存储层无明文业务写入口。
