# ADR-001 · 金额精度：分为单位整数

| 项 | 值 |
| --- | --- |
| **状态** | 已采纳（Accepted） |
| **日期** | 2026-10-30 |
| **决策者** | 主理人 / 架构师 / 工程师 |
| **关联需求** | A-02 ①②③④、Q3、NF-S-3、R9 |

---

## 背景

记账工具最常见的差评是「**求和对不上账**」。根因几乎总是浮点数：

```ts
0.1 + 0.2 === 0.3;              // false
sum([12.34, 12.34, 12.34])      // 37.019999999999996
```

账单要支持**累加、分组小计、跨月统计、导出对账**，任何一次浮点误差都会在汇总时被放大，
最终让用户对不上账、进而放弃工具。

同时，账单数据来自 CSV，源文件里的金额是**十进制字符串**（`"1,234.56"`、`"¥12.34"`、`"（35.00）"`、
全角数字、Excel 序列号日期等），解析环节本身也容易引入误差。

因此需要在「**存储精度**」「**解析精度**」「**累加精度**」三处同时做出选择。

---

## 决策

### 1. 存储与计算一律用「分为单位的整数」

- `Bill.amountMinor: number`，单位为**分**（CNY 下 1 元 = 100 分）。
- 数值**恒为正数**；收支方向由独立的 `direction` 字段表达（`income` / `expense` / `refund`）。
- 金额**不使用浮点数做任何中间计算**；求和走 `sumMinor()`，格式化走 `formatMinor()`。

### 2. 解析全程用字符串切分，不经过 `parseFloat`

`parseAmountToMinor()` 的实现要点：

- 先剥离货币符号（`¥` `￥` `RMB`）、千分位（`,`）、全角空格与全角数字；
- 再按**小数点**切分成整数部分与小数部分，用**字符串转整数**（逐位乘 10）得到最小单位整数；
- 小数位数**超出币种精度时直接判非法**（如 JPY 是 0 位小数，`"12.34"` 报错），
  **绝不静默截断**——静默截断等于悄悄改用户的账。

### 2.1 负号口径统一由 `normalizeAmountText()` 维护

「剥离货币符号」必须发生在「识别负号」**之前**——`"￥-35.00 元"` 这类写法的负号在货币符号之后，
若先识别负号就看不到 `-`，会被误判为「无法解析为数字」（系统设计 §7 T02 交付内容 2 明确要求支持该写法）。

负号口径由 `packages/core/src/money/amount-sign.ts` 的 `normalizeAmountText()` **统一维护**，
被两处共用：

| 使用方 | 用途 |
| --- | --- |
| `money/amount.ts` → `parseAmountToMinor()` | 决定返回值是否为负 |
| `csv/direction.ts` → `detectAmountSign()` | 决定「负号 = 支出」 |

这样「金额能被解析成负数」与「方向能判定为支出」永远一致，
不会出现「金额解析成功但方向判不出」的口径漂移。

### 3. 币种精度由常量表决定，金额字段带 `currency`

`money/currency.ts` 维护 `CurrencyCode → 小数位` 映射：

| 币种 | 小数位 | 示例 |
| --- | --- | --- |
| CNY / USD / EUR | 2 | `12.34` → `1234` |
| JPY / KRW | 0 | `1234` → `1234` |
| KWD / BHD | 3 | `1.234` → `1234` |

本期**仅支持 CNY**（Q3 裁决），但 `currency` 字段已在 `Bill` 上预留，
未来扩展不需要改存储结构（AS-6）。

### 4. 负数只允许出现在「解析阶段」

方向由 `direction` 表达，因此账单落库时 `amountMinor` 恒为正。
`parseAmountToMinor(raw, { allowNegative: true })` 仅在**方向推断需要读符号**时使用
（`DirectionResolver.resolveBySign` 读的是**原始文本**的符号，不是解析后的数值）。

## 备选方案与不选原因

| 备选 | 不选原因 |
| --- | --- |
| **浮点数（`number` 存 `12.34`）** | 累加误差随行数放大，账单对不上账——这正是本工具要解决的核心痛点 |
| **以「元」为单位的整数**（`12` 表示 12 元） | 丢失小数精度，等同于把金额向下取整 |
| **定点数 / 专用 decimal 库** | 需要引入第三方依赖或自研十进制类型；对「分为单位整数 + 币种精度表」这个场景是过度设计 |
| **存十进制字符串** | 排序与聚合需要在内存里二次解析，性能差；且字符串比较在「12.00 vs 12.0」上会出错 |
| **静默截断超精度小数** | 「用户写 12.34，系统存 12.30」是**悄悄改账**，比报错严重得多 |
| **金额允许为负，用符号表达方向** | 退款场景会出现「支出 + 负金额」这种双重语义，统计口径极易出错（Q8 裁决：退款用独立的 `direction: 'refund'`） |

---

## 后果

### 正面

- **求和恒等于精确值**：`sumMinor([...100 次 12.34])` 恒为 `123400`，零浮点误差（单测已断言）。
- 解析与存储的精度**一致**：解析结果就是存储值，中间没有第二次舍入。
- 币种扩展只需加一条常量表记录。

### 负面 / 代价

- **可读性下降**：数据库里看到 `3550` 而不是 `35.50`，所有展示都必须经过 `formatMinor()`。
  这是**刻意的**：展示层格式化是纯函数、可单测，且系统设计 §8.2 明确禁止把格式化结果回写存储。
- **与外部系统对接需要换算**：导出 CSV 时要除以 100 并保留 2 位小数（未来 A-24 导出功能要注意）。
- **前端展示必须始终带上币种**：`formatMinor(1234, 'JPY')` 与 `formatMinor(1234, 'CNY')` 结果不同。

### 需要注意的坑

- `amountMinor` 是 `number`（JS 的 53 位整数），安全上限是 `2^53` 分 ≈ **90 万亿元**，
  远超个人记账场景，但**不可用于金额累加到企业级**（未来如需支持，走 `bigint` 或字符串整数）。
- 任何绕过 `parseAmountToMinor` / `formatMinor` 直接做算术的代码都是 bug——代码评审要盯这一点。

## 关联需求

- **A-02 ①**：金额统一用「分」表示 —— 本决策的实现基础。
- **A-02 ②**：金额**恒为正**，方向由 `direction` 表达（退款用 `refund`）。
- **A-02 ③**：累加全程零浮点。
- **A-02 ④**：支持多币种精度表（本期仅 CNY，`currency` 字段预留）。
- **Q3**：主理人裁决「分为单位整数 + `currency` 字段；v1 仅 CNY」。
- **NF-S-3 / R9**：金额格式与系统设计 §8.2 一致（代码评审 + 单测双重把关）。
