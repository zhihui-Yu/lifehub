# ADR-006 · 索引明文列：保留 7 个不含业务语义的字段

| 项 | 值 |
| --- | --- |
| **状态** | 已采纳（Accepted） |
| **日期** | 2026-10-30 |
| **决策者** | 主理人 / 架构师 / 工程师 |
| **关联需求** | X-09、A-09、A-12、NF-S-1、X-15、R5 |

---

## 背景

端到端加密意味着**存储层看不到任何业务语义**。但三件事必须在存储层完成，
否则列表页与同步就没法做：

| 需求 | 需要的能力 |
| --- | --- |
| 账单按本地日历日分组（A-09 ③） | 按 `localDate` 范围查询 + 排序 |
| 列表按时间倒序展示 | 按 `occurredAt` / `updatedAt` 排序 |
| 增量同步（X-01 ④） | 找出「上次同步之后变更」的记录 |
| 幂等导入判定（A-12 ②） | 按 `fileHash` 查已有批次 |

如果坚持「存储层零明文」，这些能力只能靠**全量解密后内存过滤**实现——
10 万行时每次列表都要解密全部记录，首屏从毫秒级退化到秒级。

同时，隐私红线要求**明文留在本机、密文才上传**。索引列是明文，因此**每一个索引列都是一次隐私让步**，
必须逐个论证，不能顺手多留。

---

## 决策

### 1. 索引明文列共 7 个，全部不含业务语义

| # | 列 | 类型 | 用途 | 隐私影响 |
| --- | --- | --- | --- | --- |
| 1 | `entityType` | `EntityType` | 分表 / 分实体类型 | 无（结构信息） |
| 2 | `localDate` | `string \| null` | 本地日历日范围查询、按日分组 | 只暴露「哪天有消费」，不暴露消费内容与金额 |
| 3 | `occurredAt` | `string \| null` | UTC 时间戳排序 | 同上 |
| 4 | `createdAt` | `string` | 创建时间排序 | 无 |
| 5 | `updatedAt` | `string` | 更新时间排序；增量同步游标 | 无 |
| 6 | `version` | `number` | 冲突合并的版本依据 | 无 |
| 7 | `deviceId` | `string` | 冲突合并决胜键 | 极低（本地生成的 UUIDv7，与硬件无关、不出本机） |

### 2. 明确排除的业务语义字段

| 字段 | 排除理由 |
| --- | --- |
| `amountMinor` | 金额是最敏感的业务数据；出现在明文索引里等于「消费水平对服务端可见」 |
| `counterparty` | 对方名称直接暴露消费对象（商户名、诊所名、贷款方名） |
| `note` | 自由文本，风险最高 |
| `direction` | 虽可由金额符号推导，但排除后「索引列不含业务语义」这条边界更干净 |
| `categoryId` | 分类反映消费习惯 |

### 3. 语义过滤一律在解密后于内存中完成

关键词搜索、方向筛选、分类筛选都**不在存储层**做，而是在解密后过滤（系统设计 §5 假设 A-8）。
这是刻意的取舍：**牺牲一点列表页性能，换取一条可验证的隐私边界。**

### 4. 索引列由仓储层手工维护，不由框架自动生成

新增实体时必须显式决定它的索引列——这是**有意保留的摩擦**：
索引列是隐私边界，自动生成会让人在不知不觉中泄露业务语义。

```ts
// packages/core/src/repositories/bill-repository.ts
await this.store.put('bill', bill, { localDate: bill.localDate, occurredAt: bill.occurredAt });
```

### 5. 存储记录里**只**有这 7 个明文列 + 密文载荷

```ts
export interface StoredRecord {
  id: string;
  entityType: EntityType;
  version: number;
  createdAt: string;
  updatedAt: string;
  deviceId: string;
  localDate: string | null;
  occurredAt: string | null;
  payload: EncryptedPayload | PlainPayload;
}
```

**审计日志**是一个特例：`AuditLog` 领域模型只有 6 个业务字段
（`id / at / action / target / deviceLabel / success`），不含存储元字段。
由 `AuditLogRepository.save()` 在**落库环节**补齐 `version / createdAt / updatedAt / deviceId`，
**领域模型保持不变**（PRD §3.1 不动）。

### 6. 备份文件与同步载荷**不含**索引明文列

- 备份文件只搬运 `ciphertext / iv / tag` + 身份与版本元信息（`EncryptedBlob` 白名单）；
- 同步载荷的 blob 字段白名单由 `SYNC_BLOB_ALLOWED_FIELDS` 固定；
- 因此**服务端连「哪天有消费」都看不到**——它只知道「有一个 blob，密文是这些字节」。

## 备选方案与不选原因

| 备选 | 不选原因 |
| --- | --- |
| **全密文 + 全量解密后过滤** | 10 万行时每次列表都要全量解密，首屏从毫秒退化到秒；不可接受 |
| **把业务字段也做成明文索引** | 直接违反「服务端只见密文」与「数据不出本机」；金额 / 对方 / 备注是最敏感的三类 |
| **加密索引 / 可搜索加密** | 需要确定性加密 + 盲索引协议，实现与运维成本极高；本期收益不匹配。可在阶段 5+ 重新评估 |
| **用哈希做索引**（如按对方名哈希） | 哈希可被字典攻击还原（对方名空间很小），且无法支持范围查询 |
| **只在内存里建索引，磁盘全密文** | 每次重启都要全量解密重建，首启体验差；且多设备同步仍需服务端可查询结构 |
| **只保留 `localDate` 一个索引列** | 增量同步需要 `updatedAt`，冲突合并需要 `version` 与 `deviceId`，排序需要 `occurredAt`；缺一个就得全表扫描 |
| **让框架自动生成索引列** | 会把业务字段悄悄带进明文，隐私边界失守 |
| **索引列也加密，同步时由客户端解密后再上传** | 服务端就看到了明文索引，违反「服务端只见密文」；且需要一套「可搜索密文」协议 |

## 后果

### 正面

- **列表页性能可控**：范围过滤在存储层完成，只有返回的那一页才解密（系统设计 §4.3 关键点 5）。
- **增量同步有游标**：`updatedAt` + `version` 足以支撑「拉取变更集」。
- **隐私边界可验证**：7 个字段逐一列举，`check-sync-payload` 与 `encrypted-store` 集成测试双重断言。
- **备份与同步泄露面最小**：服务端只有密文字节，**连消费日期都看不到**。
- **语义过滤逻辑集中**：关键词 / 方向 / 分类过滤都在一处，便于后续加「可搜索加密」时替换。

### 负面 / 代价

- **`localDate` 与 `occurredAt` 确实是明文**：如果用户在本机被恶意软件读取数据库，
  攻击者能看出「哪些天有消费」「消费的时间点」——但**看不出买了什么、花了多少**。
  这是明文索引不可避免的残余风险，必须在隐私声明中**明确告知**（README §6.9）。
- **语义过滤在内存中做**：解密成本随数据量线性增长；10 万行时首屏仍有压力，
  需要配合虚拟化列表与分页。
- **索引列要手工维护**：新增实体时容易漏配或错配（漏配 → 范围查询失效；错配 → 语义泄露）。
- **备份恢复后索引丢失**：备份文件不含索引列，恢复后 `localDate` / `occurredAt` 为 `null`
  （语义是「未知」），需要重新索引才能按日期查询。

### 需要注意的坑

- **不要用 `occurredAt.slice(0, 10)` 当 `localDate`**：那是 UTC 日期，不是用户日历日（ADR-002）。
- **审计日志的落库要补齐存储元字段**：否则 `EncryptedStore.extractMeta()` 会抛
  `LIFEHUB_E_VALIDATION`，而 `AuditLogger.log()` 会**静默吞掉异常** → 审计全部丢失。
  这是一个「失败不显形」的坑，靠集成测试守住。
- **索引列写入时不要写业务语义**：`EncryptedStore.put()` 的 `index` 参数只接受
  `localDate` 与 `occurredAt` 两个可选项，其余元字段由实体自带。

## 关联需求

- **X-09**：索引明文列的范围与用途。
- **A-09 ③**：按 `localDate` 分组展示。
- **A-12 ②**：幂等导入依赖批次文件的哈希索引查询。
- **NF-S-1**：存储层检索不到任何明文业务数据。
- **X-15**：合规自检清单（索引列范围需在 README 与本 ADR 中**明确披露**）。
- **R5**：同步载荷与备份只含密文。
