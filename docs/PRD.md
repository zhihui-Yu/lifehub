### 1.1 原始需求复述

构建一个跨端、本地优先、端到端加密的个人生活数据管理工具。用户在完全自主的前提下导入自己导出的账单文件（CSV / Excel / PDF / txt），系统通过可配置的列头映射与分类规则将其转为结构化账单；用户在课表中管理时间块、在习惯模块打卡、在树洞日记中记录加密内容，并可选择用自己的 API Key 做本地 AI 分析。核心约束不可违反：**服务端只存密文 blob、密钥永不上传、忘记密码即数据永久丢失**；不采集手机号 / 设备号 / 定位 / 通讯录；不做银行 API 直连；AI Key 存用户钥匙串、请求不进开发者服务器；个人主体小程序不做金融分析 / AI 问答 / 公开 UGC。

## 2. 产品定义

### 2.1 产品目标（3 个正交目标）

| ID | 目标 | 含义 | 可衡量指标 |
| --- | --- | --- | --- |
| **G1 数据主权** | 任何数据在离开用户设备前已完成加密；服务端、第三方、开发者均无法获得明文；用户拥有且仅拥有解锁钥匙 | 不是「我们承诺不偷看」，而是「技术上做不到」 | ① 加密模块网络出口数 = 0（自动化断言）；② 服务端存储表中明文可读字段数 = 0；③ 主密码与派生密钥不出现在任何网络请求、日志、备份文件中 |
| **G2 零摩擦录入** | 任意来源的账单文件到结构化可用数据的路径极短；同格式文件复用既有映射与规则，一次配置长期复用 | 用户不为「适配别人家的表格格式」付出重复劳动 | ① 新格式首次导入 ≤ 3 次点击 + 1 次拖拽映射；② 同格式二次导入 ≤ 1 次点击（命中规则模板）；③ 导入 10 万行解析 + 映射 ≤ 3s（Chrome 中端机） |
| **G3 跨端一致可用** | 本地优先：断网可用；联网只同步密文差异块；多端并发编辑不丢数据、不重复 | 一份数据在手机 / 电脑 / Web 上表现一致，且离线不残废 | ① 断网状态下全部已实现功能可正常使用；② 同步通道传输内容 100% 为密文 blob；③ 双端并发修改同一记录后两端最终一致，且无字段被静默覆盖丢失 |

> 三者正交：G1 管**安全边界**，G2 管**录入效率**，G3 管**可用性与一致性**。任一目标的达成都不可牺牲另外两个（例：为 G2 便利而把明文上传云端，直接违反 G1，属否决项）。

### 3.2 精度与时间规范（强约束，先于实现锁定）

| 主题 | 决策 | 理由 | 反例（禁止） |
| --- | --- | --- | --- |
| **金额** | 一律用**分为单位的整数**（`amountMinor: number`，正负由 `direction` 表达）+ 独立 `currency` 字段（ISO 4217，如 `CNY`） | 浮点在累加与比较上必然产生舍入误差；账单求和会直接对不上 | `amount: 12.34`、`parseFloat` 求和、`toFixed(2)` 后参与运算 |
| **金额展示** | 展示层做 `amountMinor / 100` 格式化，格式化只用于渲染，不回流为存储值 | 单一数据源，避免展示精度污染存储 | 把格式化字符串回写数据库 |
| **多币种小数位** | v1 仅支持 `CNY`（2 位小数）。`currency` 字段预留；`JPY`（0 位）/ `KWD`（3 位）在阶段 2 后按需引入 `exponent` 查表 | 早期锁定小数位表可避免后期改表 | 假定所有货币都是 2 位小数 |
| **时间戳** | 存储一律 **ISO 8601 UTC**，形如 `2024-01-15T08:30:00.000Z` | 唯一无歧义、可排序、可跨端比较 | 本地时间字符串、无时区的 `2024-01-15 08:30` |
| **日历日期** | 另存 `localDate`（`YYYY-MM-DD`），按**用户当前时区**把 `occurredAt` 换算得到 | 「跨天」「今天」「本周」必须按用户本地日历算，不能按 UTC 截断 | 用 `occurredAt.slice(0,10)` 当本地日期 |
| **原始时区** | 账单额外存 `sourceTimeZone`（IANA 名，如 `Asia/Shanghai`），导入时从文件/系统推断 | 保留来源语义，便于纠错与跨时区旅行场景 | 只存 UTC，丢失来源时区 |
| **时间块时刻** | 课表用 `HH:mm` 本地墙钟时间 + `weekday`/`rrule`，**不转 UTC** | 课表是墙钟语义（每周二 8:00 就是 8:00），转 UTC 会造成跨时区漂移 | 把 8:00 转成 UTC 存储 |
| **RRULE** | 统一 RFC 5545 子集：`FREQ`、`INTERVAL`、`BYDAY`、`BYMONTHDAY`、`UNTIL`、`COUNT`；时区用 `TZID` | 唯一被广泛验证的重复规则标准 | 自造「每周重复」JSON 结构 |
| **跨天判定** | 一切「是否今天」「是否连续」判定以 `localDate` 字符串比较，不做时刻差计算 | 字符串比较免疫时区与夏令时误差 | 用 `occurredAt` 做毫秒差判断跨天 |
| **连续天数** | 以 `localDate` 集合的相邻日期差计算；缺一天即中断（连续天数重置，历史最长保留） | 语义明确、可测 | 只累加打卡次数当连续天数 |

### 3.3 E2EE 密钥与密文结构（红线级规范）

| 概念 | 规范 |
| --- | --- |
| **口令 → 主密钥** | `scrypt(password, salt, N=2^15, r=8, p=1, dkLen=32)`；`salt` 16 字节随机；KDF 参数序列化进 `VaultParams`，以便未来升级参数时用旧参数校验再用新参数重派生 |
| **主密钥用途** | 仅用于**加密解密数据密钥**与**解密「正确口令」哨兵**；不直接加密业务数据 |
| **数据密钥（DEK）** | 每个数据域（bill / diary / …）一把 256 位随机 DEK；主密钥包裹（wrap）DEK 后存储 |
| **业务数据加密** | `AES-256-GCM`，每条记录独立 96 位随机 IV；AAD 绑定 `entityType + entityId + keyVersion`，防止密文跨记录搬移 |
| **口令校验** | 用主密钥加密一段固定哨兵明文 `lifehub:verify:v1`；解锁时解密成功即口令正确，**不存储口令哈希**（哈希可被离线爆破，密文哨兵同理但需完整参数） |
| **服务端可见性** | 服务端仅存 `EncryptedBlob`（ciphertext / iv / algorithm / keyVersion / updatedAt / version）与账户标识；**不存 salt、不存 DEK、不存明文派生参数以外的任何业务语义** |
| **密钥轮换** | 改主密码 → 生成新 salt 与新主密钥 → 用新密钥包裹**旧 DEK**（双重包裹）→ 后台逐条用旧 DEK 解密、新 DEK 加密并更新 blob → 旧密钥材料销毁；全过程可中断、可续跑 |
| **恢复码** | 一次性生成的 12 组 × 6 字符 Base32 助记码（带校验位），等价于一把「恢复 DEK」；用户可单独下载「盐值备份文件」（salt + KDF 参数 + 哨兵密文），二者**任一**均可解锁 |
| **AI Key** | 存浏览器 `localStorage` 之外的用户钥匙串（Web 端用 IndexedDB 加密条目，由主密钥包裹；App 端用 Keychain / Android Keystore），**永不写入同步 blob、永不上传** |

## 5. UI 设计稿描述（本轮 4 个页面）

### 5.0 全局布局与设计约定

- **框架**：React 18 + MUI v6（组件基座：Button / TextField / Select / Dialog / Snackbar / DataGrid 或等价虚拟列表）+ Tailwind CSS（间距、栅格、响应式）。
- **布局**：桌面端左侧固定导航（220px）＋ 右侧内容区（最大宽 1280px）；窄屏（< 900px）折叠为底部 Tab 导航。

- **文案**：全中文，专业术语保留英文原词（如 `AES-GCM`、`RRULE`、`IndexedDB`）以便检索。
- **可访问性**：键盘可达（Tab 顺序合理）、对比度 ≥ 4.5:1、所有图标按钮带 `aria-label`。

### 6.2 技术栈决策与权衡（核心分歧点）

**分歧**：需求文档第 3 节指定 Flutter 为 App / Web 主战场，但本机 Flutter SDK 未安装。

**决策：本轮 Sprint 0 采用 Vite + React + TypeScript 交付「Web 可跑 MVP」，核心逻辑层保持纯 TypeScript、零 DOM 依赖。**

**理由**

1. **与需求文档自身一致**：3.4 节明确「**Web 优先** + Android 优先，小程序最后做阉割版」「禁止一上来全端一起生成」。Web MVP 本就是路线图上的第一个可交付物（阶段 2 = W3-4），并未违背文档。
2. **零阻塞**：Vite + React 项目在 Windows + Node v22 上 `npm create` 后即可运行，无需额外 SDK、模拟器、Android SDK/NDK/JDK 或真机。
3. **核心层本来就与 Flutter 解耦**：需求文档 3.1 的架构图里「核心逻辑层（TypeScript）」独立于 Flutter UI 层。本轮把这一层做成**真正可移植的纯 TS 包**，等于把 Flutter 迁移的绝大部分风险提前暴露并消化掉 —— 等 SDK 就位时，只需重写表现层，核心层可复用或经 FFI / JS 互操作（quickjs / dart ffi）调用。
4. **阶段 2 本来就要做 Web 记账 MVP**：Sprint 0 提前搭好 Vite 工程不算浪费，阶段 2 是在此基础上加图表与规则引擎，不是推倒重来。

**备选方案与不选原因**

| 备选 | 不选原因 |
| --- | --- |
| A. 先安装 Flutter SDK 再开工 | 阻塞本轮交付（下载 + 配置 Android 工具链，Windows 上往往还需重启终端 / 环境变量）；而 Sprint 0 的 4 项交付**没有一项依赖 Flutter 渲染**，装 Flutter 对本轮零收益 |
| B. Flutter Web 与 Vite 双轨并进 | 违背「每次只做一件事」；双轨会让同一批核心逻辑被两种框架约束，徒增返工与测试矩阵成本 |
| C. 直接用 Flutter Web 产物作为唯一交付 | 当前环境无法构建；且即便装好，产物体积与调试链路在 Web 快速迭代场景不如 Vite 轻量 |

**关键约束（写死，不可妥协）**

- 核心逻辑层（数据模型 / 加密封装 / CSV 解析 / 规则引擎 / 统计 / Prompt 组装 / 同步协议）**必须放在独立 TS 包中**，禁止引用 `window`、`document`、`localStorage`、任何 React 概念；依赖注入 `CryptoProvider` 与 `StorageAdapter` 两个接口（X-08、X-09）。
- 目录结构建议 `packages/core`（纯 TS）+ `apps/web`（Vite + React）+ 预留 `apps/app`（Flutter）。
- 未来 Flutter 接入的三条路径（供架构师评估，本轮不实现）：① 将 `packages/core` 逻辑移植为 Dart（语义一一对应，成本最高但最干净）；② 通过 `dart:ffi` 调 Rust/C 实现的加密核心；③ 通过 JS 互操作运行时（quickjs / JSC）在 Flutter 内执行同一份 TS 核心（成本最低、体积与性能代价最大）。**建议：架构师在设计阶段即确定加密核心的可移植边界（AES-GCM + scrypt 应尽量走平台原生实现，而非纯 TS 实现）**。

**风险与缓解**

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 未来 Flutter 复用 `packages/core` 时发现 API 不合 Dart 习惯 | 返工 | 核心层用「纯数据 + 纯函数」风格编写，避免类继承与框架耦合；字段命名保持一致以便一一映射 |
| Web 端 scrypt 性能不足导致解锁等待过长 | 体验 | 参数可配（`N` 可降级），并记录耗时；口令派生耗时纳入性能验收（X-07 相关） |
| 纯 TS 的 AES-GCM 实现性能不足 | 大数据量加密慢 | 优先用 WebCrypto / Node `crypto` 原生实现，TS 仅作兜底与接口抽象 |

| **Q3** | **金额精度口径确认** | **分为单位整数 + `currency` 字段；v1 仅 CNY** | 浮点累加必然出错，账单求和是对不上账的主因；整数分是行业通行做法 |
| **Q4** | **口令派生算法选 scrypt 还是 Argon2id？** | **scrypt**（WebCrypto 无原生 Argon2，Argon2 需 WASM 依赖，增加供应链与体积成本） | scrypt 纯 TS 成熟实现、参数可配、易于跨端一致；后续如需升级 Argon2，`VaultParams` 已预留参数序列化字段 |
| **Q5** | **可接受的解锁耗时上限？** | **0.3 – 1.0 秒**（`scrypt N=2^15`） | 太快削弱抗爆破能力，太慢影响日常体验；建议以 P95 ≤ 1s 为验收线，并保留降级参数开关 |
| **Q6** | **恢复码形态确认（是否接受「丢了就真没了」）** | **12 组 × 6 字符 Base32 助记码 + 独立盐值备份文件，二者任一可解锁** | 与「忘记密码即数据永久丢失」红线自洽；多介质备份可显著降低真实丢失率 |
| **Q7** | **本地存储选型：Web 用 Dexie 还是原生 IndexedDB？** | **Dexie**（类型友好、迁移与索引 API 成熟、体积可接受） | 需在架构阶段确认；若要求零依赖则退回原生 IndexedDB 封装（成本更高） |
| **Q8** | **退款的表达方式？** | **新增 `direction` 值 `'refund'`，金额为正** | 若用「支出 + 负向标记」表达，退款在统计与分类上会被算成负支出，统计口径易错 |
| **Q9** | **同步服务部署目标环境？** | **用户自托管（Docker Compose），支持 NAS / VPS / 内网三种** | 符合「自托管 + 不承诺长期可用性」的定位；若要官方托管需重新评估密钥托管红线 |
| **Q10** | **小程序轻量版是否真的要做？** | **最后做，且在主体与类目备案完成后启动；个人主体下必须砍掉金融分析、AI 问答、公开 UGC 部分** | 需求文档已把它排到最后；主体未落地前做会白做并有合规风险 |
| **Q11** | **是否需要「多设备邀请 / 共享密钥」能力？** | **本期不做**（AS-2 单人自用）；阶段 5 同步设计时预留 `deviceId` 与授权表结构即可 | 引入后需处理设备吊销与密钥再分发，安全面显著扩大 |
| **Q12** | **日记是否允许图片附件？** | **本期仅文本；图片放 P2，语音放 D-04（P2）** | 附件会显著放大存储与加密策略复杂度（缩略图、大小限制、流式加密） |

## 8. 非功能需求

### 8.1 性能

| ID | 指标 | 目标值 | 验证方式 |
| --- | --- | --- | --- |
| **NF-P-1** | CSV 解析吞吐 | 10 万行 / 10MB ≤ 3s（Chrome 中端机，2024 款办公本） | 基准测试脚本 + CI 性能回归 |
| **NF-P-2** | 账单列表渲染 | 1 万条数据首屏 ≤ 1s；滚动 FPS ≥ 50 | Lighthouse + 滚动性能录制 |
| **NF-P-3** | 口令派生耗时 | P95 ≤ 1.0s，且 ≥ 0.3s（低于 0.3s 视为强度不足并提示调高参数） | `crypto.scrypt` 实测 |
| **NF-P-4** | 加密吞吐 | 单条记录加解密 ≤ 1ms；1 万条批量 ≤ 3s | 基准测试 |
| **NF-P-5** | 图表渲染 | 5 年 / 10 万行数据图表首屏 ≤ 1.5s | 基准测试 |
| **NF-P-6** | 冷启动 | 本地 Web 应用首次可交互 ≤ 2s | Lighthouse |
| **NF-P-7** | 存储写入 | 单条账单落盘（含加密）≤ 5ms | 实测 |

### 8.2 安全

| ID | 要求 |
| --- | --- |
| **NF-S-1** | 全部落盘业务数据（账单、日记、分类、模板）**加密后写入**；存储层不得存在明文写入旁路 |
| **NF-S-2** | 主密码与派生密钥**永不离开客户端内存**，不落盘、不入日志、不进同步载荷 |
| **NF-S-3** | 加密算法固定为 AES-256-GCM；每条记录独立随机 IV；AAD 绑定实体身份 |
| **NF-S-4** | 篡改检测：ciphertext / IV / AAD 任一被改动时解密必须失败且不返回部分明文 |
| **NF-S-5** | 依赖治理：生产依赖锁定版本并启用完整性校验；禁用存在已知高危 CVE 的版本；不引入来源不明的脚本 |
| **NF-S-6** | 加密模块零网络出口（静态检查 + CI 断言，见 X-01） |
| **NF-S-7** | 密钥轮换可中断、可续跑、可验证（旧密文在轮换后 100% 可解） |
| **NF-S-8** | 恢复码具备校验位，输错可识别；恢复流程有速率限制（防止本地暴力枚举） |
| **NF-S-9** | 依赖漏洞扫描纳入 CI；高危漏洞阻断发布 |

### 8.3 隐私

| ID | 要求 |
| --- | --- |
| **NF-PR-1** | 不采集手机号、设备号、IMEI、定位、通讯录、相册（语音日记除外）、剪贴板 |
| **NF-PR-2** | 无埋点、无第三方统计 SDK、无广告 SDK；无任何指向外部域名的请求（CSP `connect-src 'self'` 强制） |
| **NF-PR-3** | 除用户自填的 AI endpoint 外，不向任何外部服务发送数据；AI 请求由客户端直连 |
| **NF-PR-4** | 隐私政策必须真实写明：加密方式与算法、数据不出本机、Key 不收集、忘记密码的后果、同步服务端仅存密文 |
| **NF-PR-5** | 审计日志本地留存，提供查看与清除入口；不随同步上传 |
| **NF-PR-6** | 用户可随时执行「导出加密备份」与「清空本地数据」，清空后不可恢复（需二次确认提示） |
| **NF-PR-7** | 不做公开 UGC / 社区 / 评论 / 分享广场（个人主体红线） |
| **NF-PR-8** | 不直连银行 / 支付平台 API；账单来源仅限用户自行导出的文件 |

### 8.4 可维护性

| ID | 要求 |
| --- | --- |
| **NF-M-1** | 核心逻辑层与表现层物理隔离：`packages/core`（纯 TS，零 DOM）与 `apps/web`（Vite + React）分离，core 的 `tsconfig` 不含 `DOM` lib |
| **NF-M-2** | 核心层对外能力全部通过接口注入（`CryptoProvider`、`StorageAdapter`、`Clock`、`Logger`），便于替换实现与测试替身 |
| **NF-M-3** | 全量 TypeScript strict 模式；禁止 `any`（必要时用 `unknown` + 收窄） |
| **NF-M-4** | 核心层单元测试覆盖率 ≥ 80%；加密、CSV 解析、日期与时区逻辑覆盖率 100% |
| **NF-M-5** | 测试夹具（fixture）外置为文件，包含跨时区、跨天、BOM、GBK、含引号与换行的边界样本 |
| **NF-M-6** | 统一代码规范与提交规范（commit message 规范 + lint + format 钩子） |
| **NF-M-7** | 数据模型变更走「schema 版本号 + 迁移函数」，迁移可回滚；新旧版本兼容窗口 ≥ 1 个大版本 |
| **NF-M-8** | 关键决策（金额精度、时间格式、加密参数、实体字段）以 ADR 形式记录在 `docs/adr/` |
| **NF-M-9** | 目录与命名保持跨端可映射：实体名、字段名在 `packages/core` 与未来 Dart 端保持同名同义，降低移植成本 |

## 9. 附录

### 9.1 术语表

| 术语 | 含义 |
| --- | --- |
| **amountMinor** | 以「分」为单位的整数金额。`1234` 表示 12.34 元 |
| **localDate** | 用户本地时区下的日历日期 `YYYY-MM-DD`，用于跨天 / 今日 / 本周判定 |
| **occurredAt** | 事件发生的绝对时刻，ISO 8601 UTC |
| **sourceTimeZone** | 数据来源的 IANA 时区名，如 `Asia/Shanghai` |
| **DEK** | 数据密钥（Data Encryption Key），直接加密业务数据的对称密钥 |
| **AAD** | GCM 的附加认证数据，绑定实体身份防搬移 |
| **vaultParams** | 加密档案：KDF 参数、盐值、口令哨兵密文、密钥版本 |
| **RuleTemplate** | 规则模板：列头映射 + 分类规则的组合，可复用 |
| **ImportBatch** | 一次导入的批次记录与统计 |
| **CompletionEvent** | 完成事件：课表与习惯共用的完成记录实体 |
| **RRULE** | RFC 5545 重复规则子集，用于课表与习惯的周期定义 |
